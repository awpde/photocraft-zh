# PhotoCraft 简体中文版 —— 维护指南

> 面向接手维护本仓库的人 / agent。
>
> 最后核对：2026-10-15（上游 v0.9.0 时期）

---

## 0. 一句话背景

用户需要 PhotoCraft（Photoshop 的纯 Rust 重写）的**简体中文 Windows 安装包**。
上游把界面译文用 `include_str!()` 编译进二进制，所以界面是不是中文只取决于编译的是哪个 commit
—— 因此本仓库**不含任何上游源码**，只在 GitHub Actions 上拉上游源码 + 做极小改动再编译。

上游与 PdfCraft 同为 MIT OR Apache-2.0 双许可（作者 storytold / ArtCraft）。
姊妹项目 `awpde/pdfcraft-zh` 见其 `docs/维护指南.md`；**本仓库刻意做得比它简单得多**，原因见 §2。

---

## 1. 与 PdfCraft 的关键差异

| 维度 | photocraft-zh | pdfcraft-zh |
|---|---|---|
| 版本数 | **单版本**（纯中文化） | 双版本（zh-hans + 含中文输入修复的 zh-cjk） |
| 改源码 | **不改** | zh-cjk 需要打补丁 |
| 字体 | **完全不处理**（见 §3） | 替换界面字体 + 字体清单校验 |
| 安装向导文案 | **极小改动**（见 §4） | **整体覆盖** `photocraft.zh-cn.wxl` |
| 图标 | 不替换 | 替换三处 |

> 「PhotoCraft 有没有 PdfCraft 那个『新增中文文字变问号』的问题？」
> —— **没有**。PhotoCraft 的 CJK 文本走运行时系统字体（`crates/text/src/cjk.rs`），
> 从设计 上就不依赖 craft-fonts 的日文字体回退，所以不需要任何源码补丁。

## 2. 仓库结构

```
photocraft-zh/
├── README.md                # 面向用户的说明
├── docs/维护指南.md          # ← 你正在读的文件
├── overrides/
│   └── photocraft.zh-cn.wxl      # 中文安装向导文案（WiX 内置 zh-CN 底座 + 我们的补充，Codepage=936）
└── .github/workflows/
    └── zh-hans-windows-build.yml
```

`overrides/` 里**只有安装界面一个文件**。这是有意的：改动面越小，上游更新时越不容易坏。

触发方式：

- **定时**：`schedule: '0 22 * * *'`（UTC 22:00 = 北京时间次日 06:00）→ 上游**最新 Release tag**
- **手动**：`workflow_dispatch` + `upstream_ref`（默认 `main`）

Release tag 命名：`zh-hans-<ref>`（`ref` 是 tag 时）或 `zh-hans-<ref>-<commit 短哈希>`（分支时）。

## 3. 字体：为什么不处理（重要，别乱加）

上游 PhotoCraft 的界面中文字体是**运行时从系统读取**的
（Windows 上取 `C:\Windows\Fonts\msyh.ttc`，即微软雅黑），见 `crates/text/src/cjk.rs`。

所以本工作流：

- **不嵌入任何中文字体** → 省掉约 8 MB 体积
- **不换字体、不做字体清单校验** → 省掉 4 个步骤
- 便携版里也**不分发字体许可文件**（因为没有随包字体）

但 `CRAFT_FONTS_REF` **仍然要锁**，锁的是**与官方发版完全一致**的那个 commit
（官方 `release.yml` 里锁的就是它）：里面是日文字体，简体中文/繁体中文不走它。
不锁也能构建（上游有 `ui_works_without_craft_fonts` 测试），但那样日文界面会退回系统日文字体，
交付物就和官方不一致了。**锁上之后，我们的包与官方的唯一差别就只有安装界面。**

## 4. 安装向导：上游原生 + 中文文案覆盖

> **2026-10-29 改版**。旧方案是「自建 installer-ui.wxs + 三处注入」，已废弃：
> 上游 photocraft v0.17.0 起自带**完整安装向导**（`<ui:WixUI Id="WixUI_InstallDir">` + 作用域选择页），
> 而我们的注入依赖上游 `photocraft.wxs` 里的两个锚点，其中 `<Property Id="INSTALLFOLDER">`
> 被上游搬进了 `install-policy.wxi` → 锚点命中 0 次 → 2026-10-29 的定时构建在应用界面步骤中止。
> 自建覆盖**每逢上游改安装界面就会失效**，这正是要摆脱的维护负担。

### 现在的做法

上游原生向导已经支持我们需要的一切：**自选安装位置**（标准「选择安装位置」页）、
**每用户 / 全机器**作用域选择（`CraftScopeDlg`）、按作用域给不同默认目录
（`install-policy.wxi` 里的 `SetProperty`，条件都是 `NOT INSTALLFOLDER`，用户选了路径就不会被覆盖）。

我们**只做一件事**：把向导文案换成中文。

```yaml
# workflow 的一处极小改动
ps1="src/packaging/windows/package.ps1"
anchor="-culture en-US -loc (Join-Path $PSScriptRoot 'photocraft.en-us.wxl')"   # 必须恰好命中 1 次
cp builder/overrides/photocraft.zh-cn.wxl src/packaging/windows/
sed 把 -culture en-US 改成 zh-cn、文案文件名换成 photocraft.zh-cn.wxl
```

- 我们用 **`-culture zh-cn`**（不是 zh-Hans）：WiX 5 自带 `WixUI_zh-CN.wxl`，向导全部页面都有中文底座，
  我们的 `overrides/photocraft.zh-cn.wxl` 只补它没有的几条（上游特有的 `PhotocraftInstallDirNote` /
  `PhotocraftAllUsers`，以及带版本号的几条）。
- **wxl 里必须写 `Codepage="936"`**（简体中文 GBK）：MSI 数据库只能存该代码页的字符，
  不设的话中文放不进去，链接期报 WIX0311（code page 1252 放不下中文）。
  内置的 `WixUI_zh-CN.wxl` 自己也是这么写的。
- **`-culture en-US` + 中文 wxl 是行不通的**（2026-10-29 实测失败）：代码页仍是 1252，报 WIX0311。
- 文案 id 用的是 WiX 标准向导的命名（`WelcomeDlgTitle` / `CommonButtonNext` / …），
  比界面结构稳定得多 —— 这是选它的原因。

### 上游更新后这一步失败怎么办

锚点命中数**不是 1** 时构建会明确失败并打印命中次数 —— 这是上游换了向导文案文件的可靠信号。

1. 下载上游最新 `packaging/windows/package.ps1`，看 `wix build` 的 `-loc` 调用变成什么了
2. 如果上游换了文案文件名 → 改 workflow 里的 `anchor` 指向新文件
3. 如果上游新增了需要翻译的文案 → 往 `overrides/photocraft.zh-hans.wxl` 里补对应 String
4. 触发构建，按 §6 铁律回读日志

> 如果上游哪天**自带了 zh-Hans 文案文件**，那就把它直接接上、删掉我们的 wxl —— 那是最好的结果。

## 5. 构建流程

```
resolve job（定时取上游最新 Release tag / 手动取输入的 ref）
keepalive job（距上次提交超 50 天补空提交，防止定时任务被 GitHub 停用）
build job:
  1-3  拉取上游源码 / 本仓库 / craft-fonts
  4    注入「自选安装位置」界面（三处锚点注入）
  5-6  安装 Rust / 缓存 cargo
  7    校验中文词条确实存在
  8-9  安装 WiX 5 → 编译打包（官方 package.ps1 → MSI + 便携版 zip）
  10   校验 MSI 带上了自选安装位置界面
  11   校验 exe 内确实含简体中文译文（deflate 还原后逐字节比对）
  12   生成许可证与改动声明
  13   上传产物 + 创建或更新 Release
```

| 变量 | 当前值 |
|---|---|
| `UPSTREAM` | `storytold/photocraft` |

## 6. 铁律

### 铁律 1 —— 永远不要只看绿对勾，必须回读构建日志

`gh run list` 显示 success **不代表**定制都生效。必须下载 build job 日志，确认：

| 要找的行 | 含义 |
|---|---|
| `✅ 已替换英文向导为 <UIRef Id="PhotocraftInstallerUI" />` | 界面注入生效 |
| `✅ 界面文件已就位：…（N 字节）` | 界面文件落地 |
| `✅ 还原后与检出词条逐字节一致（N 字节，含简体中文）` | exe 里的译文完好 |
| `✅ 简体中文译文已以压缩形式编入 exe` | 中文确实编进去了 |
| `✅ InstallLocationBrowser` / `LocationPath` / `LocationBrowse` / `WIXUI_INSTALLDIR` / `_BrowseProperty` / `SetTargetPath` / `DirectoryListUp` | 自选安装位置界面完整 |
| `✅ 许可证与改动声明已生成` | 合规四件套齐全 |

### 铁律 2 —— 任何字符串前缀/比较判断必须用 `Ordinal` ★

见 §7.1，这是本仓库最隐蔽的坑，**已经让构建连续失败 4 次**。

### 铁律 3 —— 上游的词条打包格式会变（v0.9.0 起）

上游 v0.9.0 把词条打包从「整表内嵌」改成了**去重格式**：
`keys.deflate` + 每语言差异 deflate，条目按 `\x01` / `\x02` 前缀 + key 偏移引用。

校验逻辑（workflow 第 11 步）必须跟着适配：**找到 deflate 产物 → 还原 → 与检出词条逐字节比对**。
上游再改格式时，会表现为「校验 exe 含译文」这一步失败，日志里会给出 packed 文本的行号。

## 7. Windows / PowerShell 踩坑集

### 7.1 pwsh 的 ICU 排序规则把控制字符视为可忽略 ★★

**这是本仓库 2026-10-12 ~ 10-15 连续 4 次构建失败的根因**，务必记住。

现象：构建都挂在「校验 exe 内确实含简体中文译文」，报

```
packed line 13: 空译文条目（0D）
```

根因链（已本地复现确认，不是猜测）：

1. 上游 v0.9.0 的 `zh-hans.tsv` 在 12 行注释头之后有**一个空行**
2. Windows runner 检出为 CRLF → 空行变成单个 `\r`（字节 `0x0D`，正好对上日志里的 `0D`）
3. 上游 `build.rs` 对非词条行「原样保留」，`\r` 进了打包数据
4. 校验循环用 **culture-sensitive 的 `StartsWith`** 判断 `\x01` / `\x02` 前缀
5. workflow 的 shell 是 **`pwsh`（PowerShell 7 / .NET Core / ICU）**，
   ICU 排序规则**把控制字符视为可忽略** → `"\r".StartsWith("\x01")` 返回 **True**
   → 空行被误判成「以 `\x01` 开头的空译文条目」

**为什么本地复现不出来**：本机是 PowerShell 5.1（.NET Framework / NLS），
同样写法返回 **False**。只有 pwsh runner 上才犯。

**修复方式（已落地）**：

```powershell
# 1) 三个 StartsWith 全部改成 Ordinal（逐字节，绕开 ICU 排序规则）
$line.StartsWith([char]0x01, [StringComparison]::Ordinal)
# 2) 显式跳过空行 / CR 行 —— 但仍要原样追加到重建文本，
#    否则后面的「逐字节比对源文件」会因为少行而失败
if ($line.Length -eq 0 -or [int][char]$line[0] -eq 13) { $sb.AppendLine($line) | Out-Null; continue }
```

**复现方法（可复用）**：把上游 `crates/ui-egui/build.rs` 的打包逻辑
（`catalog_entry` + 打包循环，约 30 行）移植到 Python，喂入 CRLF 版词条，
即可精确复现 CI 的 packed 数据，再用 PowerShell 跑校验逻辑。

> **通用教训**：「本地过了 CI 挂了」时，第一反应就怀疑 pwsh/ICU 与 5.1/NLS 的差异。

### 7.2 CRLF 污染

做字符串锚点匹配前**必须先归一化** `content.replace('\r\n','\n')`。
远端 workflow 文件可能是 CRLF（Windows 上编辑留下的），否则锚点命中 0 次，
会报出「已被他人改动」的误判。

### 7.3 含中文的 `.ps1` 文件必须加 UTF-8 BOM

否则 PowerShell 5.1 按 ANSI 解码 → 语法错误（表现为莫名其妙的「字符串缺少终止符」）。
测试脚本建议直接写纯英文。workflow 里内联的 pwsh 脚本不受影响（pwsh 默认 UTF-8）。

### 7.4 本机没有 git 和 patch

维护用的 Windows 机器**没有安装 git，也没有 GNU patch**。
需要做补丁类工作时用姊妹项目的纯 Python 实现（见 §10）。

### 7.5 PowerShell 里调用 `gh` 的参数解析

`gh api ... --jq '.[] | ...'` 在 PowerShell 下常被拆成多个参数而报
`accepts 1 arg(s), received 2`。改用 Python 走 curl + JSON 解析。

## 8. 运维速查

### Release 是否真的更新了 —— 看资产的 `updatedAt`，不是 `publishedAt`

`publishedAt` 是**首次**发布时间；同名 tag 重新构建后资产会替换但 `publishedAt` 不变，
极易误判成「没更新」。

### 推文件到仓库

用 `gh api --method PUT repos/awpde/photocraft-zh/contents/<path>`（更新要带 `sha`），
**别用 git push**（schannel 证书问题）。

### 给用户的下载链接

用户**非程序员、不熟 GitHub 网页**，必须给**可直接点开的完整 URL**：
https://github.com/awpde/photocraft-zh/releases （认 Latest 徽标）或 asset 直链。

## 10. 风险表

| 风险 | 触发条件 | 处理 |
|---|---|---|
| **译文校验误判** | 上游词条文件出现新的空行 / 换行差异 | §7.1。必须用 `Ordinal`，且跳过空行时仍要原样追加 |
| 界面注入锚点失效 | 上游改 `photocraft.wxs` 或 `package.ps1` | §4。锚点命中数会明确报出来 |
| 上游改词条打包格式 | 上游 build.rs 再改打包逻辑 | 铁律 3 + §7.1 的复现方法 |
| 上游没有简中词条 | 构建了不含 `zh-hans.tsv` 的版本 | resolve job 会识别并跳过，不会产出英文包 |
| craft-fonts 结构变化 | `CRAFT_FONTS_REF` 锁定的 commit 被删 / 改名 | 换成官方 `release.yml` 里当前锁定的 commit |

## 11. 用户偏好与合规（务必遵守）

- **非程序员、不熟 GitHub**：下载链接必须是可直接点开的完整 URL
- **不想机器上堆文件**：大文件给直链自己下；临时目录用完问是否清理
- **不要自动生成交接文档**：维护知识以本文件为准，需要更新时再改
- **release 清理**：偏好「留最新各一版」，但删旧 release 前**先问**
- **合规四件套**必须随包：`LICENSE-MIT.txt`、`LICENSE-APACHE.txt`、NOTICE、`UNOFFICIAL-BUILD-zh-CN.txt`
- 改动声明里必须写明「界面中文字体使用系统字体（Windows 上为微软雅黑），因此本包不分发中文字体」
